## ほかのサイトの調査 (2026-10-28)

ChatGPT の不具合は「サイトがトップレイヤーに要素を出すと、その透明な `::backdrop` でアイコンが覆われたと判定される」ことが原因だった。ほかのサイトでも同じことが起きるかを、ログインなしの画面で調べた。

調べ方は 3 つ。

- 読み込まれた JavaScript の中の、トップレイヤーを使う呼び出しを数えた。対象は `showPopover`、`popover` 属性、`showModal`、`requestFullscreen`、`::backdrop`
- 画面のメニューを開いて、トップレイヤーに入る要素を確かめた
- 拡張機能を読み込んで、アイコンの位置を確かめた

| サイト | 分かったこと | アイコンへの影響 | 確かさ |
|---|---|---|---|
| ChatGPT | ファイルを開くと、パネルのつまみ (`div[popover=manual].group/panel-resizer`) がトップレイヤーに入り、開いている間ずっと残る。膜は消されていない (利用者の画面での診断) | 1.7.0 では押せない。1.7.1 で直した (D-31〜D-36) | 高 (利用者の画面で確認) |
| Gemini | メニュー (モード選択など) は Angular CDK のオーバーレイで、`popover="manual"` としてトップレイヤーに入る。膜は `.cdk-overlay-popover::backdrop{display:none}` で消されている。設定のメニューやツールのメニューはトップレイヤーに入らない | メニューが開いていて、その箱がアイコンに重なるときだけ覆われる。それはサイトの部品が上にあるのが正しい状態 (D-33 で上に戻らない)。閉じれば元に戻る | 高 (実際の画面で確認) |
| Gemini (位置) | 入力欄の白い箱が入力欄の 9 段上にあり、アイコンの位置を決める箱を見つけられなかった。アイコンが入力欄そのものの右、つまりモード選択のボタンの上に重なっていた | 1.7.1 で直した (D-37、T-27) | 高 (実際の画面で確認) |
| Manus | トップレイヤーを使うのは 3 か所だけ。<br>・ドラッグ中の部品 (膜は消されている)<br>・追加機能を開くモーダル<br>・スライドなどの全画面表示<br>メニューと動画のモーダルはトップレイヤーに入らない | 普段のチャットでは影響しない。モーダルの間はアイコンが下に残る (設計どおり) | 中 (ログイン後の `/app` は未確認) |
| Claude | Cloudflare の確認画面が出て、自動のブラウザでは調べられなかった。確認画面の突破はしていない | 不明 | — |

ログイン後の画面 (Claude 全体、Gemini の Canvas、Manus の `/app`) は自動では開けない。1.7.1 では、アイコンへのクリックを受け付けなかったとき、その時トップレイヤーにあった要素の説明を動作ログに残す。だから、ほかの画面で同じことが起きても、ログのタブから原因が分かる。

調べたときのスクリプトと結果は、作業用の一時ディレクトリに置いた (リポジトリには入れない)。

## Secure Composer (ChatGPT の保護入力欄) の修正

利用者が開発版の 1.7.1 を、ログイン後の ChatGPT (暗い表示) で確かめた (2026-10-28)。そのとき報告された 3 つの症状と、調べて見つけた 1 つの問題。どれも 1.7.0 の Secure Composer (`plans/feat-secure-composer-2026-10-18.md`) から起きていた。

### 問題

| ID | 問題 | 原因 |
|---|---|---|
| P-SC-01 | 入力欄の背景が白い (暗い表示なのに) | `chatgpt-composer-adapter.js` の `readTheme()` は、入力欄から 6 段上までの祖先で背景色を探す。ChatGPT の入力欄の角丸の箱 (半径 28px) は 8 段ほど上にあり、届かなかった。見つからないときは `<html>` の `dark` クラスで決めていたが、今の ChatGPT は `class="chatgpt-theme"`、`data-theme="dark"`、`color-scheme: dark` で、明るい表示と取り違えて白にしていた (利用者の画面での診断) |
| P-SC-02 | マスキングがオフで個人情報を入れても、アイコンが黄色にならず、内訳も出ない | ChatGPT では下書きが iframe の中にあり、アイコン (composer-toggle) は読めない。オフの警告を iframe 側に移す作業が、1.7.0 で残課題のままだった (同 plan の「残課題 4」)。ストアの説明と告知は「オフでも黄色になる」と書いている |
| P-SC-03 | 複数行を書くと、入力欄の中で縦にスクロールしないといけない | iframe の中の `autosize()` は高さの上限を `window.innerHeight * 0.45` で計算する。iframe の中の `window.innerHeight` は iframe 自身の高さ (1 行分) なので、上限が 1 行未満になり、伸びられなかった。CSS の `max-height: 45vh` も同じ |
| P-SC-04 | 除外リストの値も伏せてしまう | iframe は常に伏せる語だけを読み、除外リスト (`maskAllowlist`) を読んでいなかった。`maskSanitize()` は除外リストを知らないので、除外した値も伏せ字にして送る |

利用者の画面での診断では、入力欄に最低の高さ (`min-height`) を付けると、ChatGPT の入力欄の箱ごと上に伸びた (入力欄の並び `data-composer-layout="multiline"` は変わらない)。

### 要件

| ID | 要件 |
|---|---|
| F-SC-14 | 保護入力欄の背景は、ChatGPT の入力欄の実際の背景色に合わせる。8 段より上の祖先にある色も、半透明の色 (下の色と重ねた結果) も扱う。見つからないときは、ページの `color-scheme` (暗い/明るい) に合わせる |
| F-SC-15 | 保護入力欄は、書いた行数に合わせて伸びる。ChatGPT の入力欄の箱も一緒に伸びる。画面の高さの 40% を超えたら、入力欄の中でスクロールする |
| F-SC-16 | マスキングがオフのとき、保護入力欄の下書きに個人情報があれば、入力が止まって 0.4 秒後にアイコンを黄色にし、内訳 (件数と種類) を出す (ほかのサイトと同じ)。iframe の外に出すのは件数と種類の名前だけで、文章や値は出さない。ページのスクリプトは警告を消したり偽ったりできない |
| F-SC-17 | 黄色の内訳の「マスキングする」で、保護入力欄の下書きを伏せ字にする。「オンにする」でマスキングをオンにする |
| F-SC-18 | 保護入力欄は除外リストの値を伏せず、オフの警告にも数えない (ほかのサイトの確認画面と同じ) |

### 設計

| ID | 決定 | 対応 |
|---|---|---|
| D-SC-01 | `readTheme()` は、入力欄から `<html>` までの祖先をすべてたどり、背景色を下から重ねる。<br>・色は canvas に塗って読み直し、`oklch()` などの書き方も RGBA にする<br>・不透明な色が出たところで止める<br>・半透明の色は、その下の色と重ねた結果にする (重ねる計算は `tint.js` の `flatten()`)<br>・`<html>` まで不透明な色が無ければ、`color-scheme` が暗いなら `rgb(33, 33, 33)`、明るいなら白を土台にする<br>あわせて、ページの `color-scheme` を iframe に渡す。iframe の中と iframe の要素の両方に同じ値を付け、スクロールバーなどを暗い表示にそろえる | F-SC-14 |
| D-SC-02 | 高さの上限は、ページ側 (アダプタ) が `window.innerHeight * 0.4` を測って iframe に渡す。iframe の中の `vh` や `window.innerHeight` は使わない | F-SC-15 |
| D-SC-03 | iframe は、下書きの高さと「空かどうか」を知らせる (「空」は、入力欄が空で、確認や案内も出ていないこと)。アダプタは、ChatGPT の入力欄 (`#prompt-textarea`) の `min-height` をその高さにする。ChatGPT の入力欄の箱が伸び、保護入力欄はこれまでどおり ChatGPT の入力欄に重なる。<br>・ChatGPT は入力欄の親 (`max-height` と `overflow: auto`) で入力欄を切り取る。親の上限より高くすると、入力欄の矩形は親の外 (下の段のボタンの上) にはみ出す。そこで保護入力欄は、入力欄の矩形を切り取る祖先と重ねた「見えている範囲」に重ねる<br>・見えている範囲が下書きの高さより低ければ (上限で止まった)、その高さを iframe の上限として渡し、iframe の中でスクロールさせる。窓の大きさが変わったら測り直す<br>・入力欄の幅が `min-height` を付けたときのままなら、下書きの高さにそのまま合わせる (1 行消せば 1 行縮む)。幅が変わったとき (ChatGPT が並びを切り替えたとき) は、1 行分を超えて低くなるまで縮めない。高さと並びが互いを変えて、行ったり来たりしないようにする<br>・送信前の確認や案内が出ているときも、全体の高さは上限の中に収める。下書きの部分を低くして中をスクロールさせ、確認のボタンは常に見せる<br>・ページが入力欄の `style` を書き換えて `min-height` が消えたら、付け直す<br>・下書きが空になったとき、保護入力欄を外すとき、入力欄が作り直されたときは、`min-height` を元に戻す<br>・ページは入力欄の高さ (行数) を知ることができるが、文字は渡らない | F-SC-15 |
| D-SC-04 | iframe は、オフのとき (オンでは要らない)、入力が止まって 0.4 秒後に、自分の中のエンジンで下書きを調べる。`maskAggregated()` を使い、除外リストの値は除く。<br>結果は `draftinfo` として、件数、種類ごとの件数 (`PERSON` などの種類の名前)、機密と思われる文の件数だけを送る。<br>アダプタは、composer-toggle の関数 (`window.__localMaskMCP.composerToggle.setScDraftInfo`) を直接呼ぶ。両方とも isolated world にあり、ページからは見えない。`window` のイベント (ページも送れる) は使わない。<br>composer-toggle は、Secure Composer が入力欄を受け持つ間、この結果をオフの警告に使う | F-SC-16 |
| D-SC-05 | 内訳の「マスキングする」は、Secure Composer が受け持つ間、アダプタの `maskDraft()` を呼ぶ。iframe は下書きを伏せ字にした文に置き換える (除外リストの値は残す)。<br>・ほかのサイトのように確認画面は開かない。確認画面はページの側 (MAIN world) にあり、下書きを見せると原文がページに渡るため<br>・置き換えは編集の操作として行い、Ctrl+Z で元に戻せる<br>「オンにする」はオンにするだけ。送るときに iframe が伏せる | F-SC-17 |
| D-SC-06 | iframe は除外リストも `chrome.storage` から直接読む (ページには渡さない)。伏せるときは `maskSanitize()` の検出から除外リストの値を除き、`aggregate.applySpans()` で伏せ字にする。<br>常に伏せる語にも入っている値は伏せる。送る前の裏取り (`findLeaks`) は、常に伏せる語の生値が残っていると送信を止めるため | F-SC-18 |

## ChatGPT で複数行の下書きを送れない不具合 (1.7.0 から)

利用者が、開発版の 1.7.1 をログイン後の ChatGPT で確かめているときに見つけた (2026-10-28、「Enter キーを押してもリクエストが送信できない」)。1.7.0 と同じコードで、公開中の 1.7.0 でも起きる。

### 問題

| ID | 問題 | 原因 |
|---|---|---|
| P-SC-05 | ログイン後の ChatGPT で、先頭の近く (16 文字以内) に改行がある下書きを Enter で送れない。保護入力欄に「送信できなかった。もう一度 Enter で送れるよ。」と出て、何度押しても同じ | アダプタの `writeNative()` は、書き込めたかを「`innerText` に下書きの先頭 16 文字が含まれるか」で確かめていた。ChatGPT の入力欄 (ProseMirror) は行を段落 (`<p>`) にし、`innerText` では段落の間が `"\n\n"` になる (下書きの改行は `"\n"`)。書き込めているのに、失敗と判定していた。モックの入力欄も `<p>` で行を作るが、テストの下書きは 1 行目が 16 文字より長かったので気づかなかった |
| P-SC-06 | 送れなかったことが動作ログに残らず、原因をたどれなかった | 送信の失敗 (書き込めない、入力欄が無い、応答が無い) を記録する出来事が無かった |

ログインなしの ChatGPT (入力欄は `textarea#mobile-composer-prompt`) では、同じ下書きでも ChatGPT の送信の手順 (`chat-requirements/prepare`) まで進むことを、送信の通信を止めた状態で確かめた。

### 要件

| ID | 要件 |
|---|---|
| F-SC-19 | 複数行の下書きも Enter で送れる。ChatGPT が行頭の `- ` や `1. ` を箇条書きに、`#` を見出しに、`**` を太字に変えても送れる |
| F-SC-20 | 送れなかったときは、下書きを残したうえで、理由を動作ログに残す |

### 設計

| ID | 決定 | 対応 |
|---|---|---|
| D-SC-07 | `writeNative()` の確かめは、書いた文と入力欄の `innerText` の両方から、空白、行頭の箇条書き・見出し・引用の印 (`-`、`*`、`+`、`>`、`#`、`1.`、`1)`)、強調の記号 (`*`、`_`、`` ` ``、`~`) を除いてから、先頭 16 文字が含まれるかで判定する。<br>書き込みが本当に失敗したとき (入力欄が空のまま) は今までどおり失敗と判定し、下書きを残す | F-SC-19 |
| D-SC-08 | 動作ログに `send.failed` (送信できませんでした) を足す。項目は `reason` と `via`。<br>・`reason` は、アダプタの返事 (`write failed`、`no native composer`、`busy`) と、iframe とアダプタの間の時間切れ (`no-response`) から決める<br>・記録するのは iframe で、文章は残さない | F-SC-20 |

### 検証

| ID | 確かめること | 場所 |
|---|---|---|
| T-SC-19 | 2026 年のログイン後の作りのモックで、`1 行目` / `- 2 行目` / 個人情報を含む 3 行目を Enter で送ると、確認バーを経て 1 回送られ、3 行とも本文に入り、個人情報は伏せ字になる。直す前のコードでは「送信できなかった」で止まる | `tests/e2e/sc-fixes-171.test.mjs` |
| T-SC-19b | モックの入力欄が書き込みを受け付けないとき (`?rejectWrite=1`)、送られず、下書きが残り、「送信できなかった」と出て、動作ログに `send.failed` (`reason: write-failed`、`via: secure-composer`) が残る | 同上 |
| T-LG-04 | `send.failed` も日本語の文になる | `tests/engine/diag-log.test.mjs` |

## ML 検出がオンだと Enter を押しても送れない不具合 (1.7.0 から)

複数行の不具合 (P-SC-05) を調べているときに見つけた (2026-10-28)。設定画面の「ML 検出を有効化」をオンにしている人だけに起きる (既定はオフ)。1.7.0 と同じコードで、公開中の 1.7.0 でも起きる。

### 問題

| ID | 問題 | 原因 |
|---|---|---|
| P-SC-07 | ML 検出がオンのとき、保護入力欄で Enter を押しても送れず、何も表示されない。もう一度押しても何も起きない。動作ログにも残らない | `submit()` は送る前に `maskSanitize()` で個人情報を検出する。ML がオンなら、その中の `callMlDetect()` (`engine/onnx-detector.js`) が Service Worker を経由して offscreen の判定を待つが、待つ時間に上限が無い。offscreen はモデルを読み込んでから判定する。モデルは初回に huggingface.co から取得して (135 MB) ブラウザのキャッシュに置き、以後はキャッシュから読み込むが、読み込みだけでも、ブラウザのキャッシュが温まるまでは 13〜22 秒かかる (下の計測。温まったあとは 1 秒前後)。取得が止まる (回線の不調、ホストの不許可) と、いつまでも終わらない。待つ間は状態 `MASKING` のまま何も出さず、`submitting` のため 2 回目以降の Enter は捨てられる。失敗ではなく「終わらない」ので、記録する出来事も起きない |
| P-SC-08 | 待っている間、利用者には何も見えない | 送る前の検出の間の表示が無かった。ML なしの検出は数ミリ秒で終わるため |

ほかのサイトの送信経路 (`injected.js` → `content.js` の `handleLocalMask()`) にも同じ待ちがあるが、ページ側の `localMask()` が 10 秒で諦めて MAIN world のエンジン (ML なし) に切り替えるため、止まりはしない (除外リストなどがあると `send.blocked` の `lists-unavailable` になる)。

計測 (2026-10-28、ヘッドレスの Chromium、Core i9-13900K、WSL2、`ML_PREWARM` と `ML_DETECT` を Service Worker に送って測った):

| 内容 | 1 回目 (取得) | 2 回目 (キャッシュ) | 3 回目 (キャッシュ) | 4〜5 回目 (キャッシュが温まったあと) |
|---|---|---|---|---|
| モデルの取得と読み込み | 56.5 秒 | 21.6 秒 | 13.4 秒 | 0.6〜1.3 秒 |
| 判定 (26 字) | 0.07 秒 | 0.06 秒 | 0.08 秒 | 0.04〜0.06 秒 |
| 判定 (2,000 字) | 0.72 秒 | 0.71 秒 | 1.03 秒 | 0.70 秒 |
| 判定 (20,000 字) | 0.90 秒 | 0.72 秒 | 1.41 秒 | 0.70 秒 |

ブラウザを起動し直すたびに読み込みはやり直しになるが、ブラウザのキャッシュが温まると 1 秒前後まで縮む。モデルは先頭の 512 トークンしか見ない (2,000 字と 20,000 字で検出の数が同じ 49)。これは 1.7.0 からの制限で、この修正では変えない。

### 要件

利用者の選択 (2026-10-28): ML が時間内に応答しなかったら、正規表現と辞書だけで伏せて送る (案 A)。送信を止める案 B は採らない。

| ID | 要件 |
|---|---|
| F-SC-21 | 保護入力欄の送信は、ML の判定を待つ時間に上限を持つ。上限を過ぎたら、正規表現と辞書の検出だけで伏せて送る。そのときは動作ログに残し、送ったあとに入力欄の下に一言出す。ML の判定が失敗したときも同じ |
| F-SC-22 | 送る前の検出に時間がかかっているあいだは、入力欄の下に「確認中…」と出す |
| F-SC-23 | ML がオンなら、対応サイトのページを開いた時点でモデルの読み込みを始める。送るときに読み込みを待たずに済むようにする |

### 設計

| ID | 決定 | 対応 |
|---|---|---|
| D-SC-09 | 上限はエンジンの `callMlDetect()` に置く (`engine/onnx-detector.js`、既定 8 秒、`opts.mlTimeoutMs` で変えられる)。上限を過ぎたら空の結果と `status: "timeout"` を返し、遅れて届いた返事は捨てる。`detectViaMl()` は `{ detections, status }` を返し、`maskSanitize()` と `maskAggregated()` は結果に `ml: { status }` を付ける (`off` / `ok` / `timeout` / `error` / `unavailable`)。ほかの経路 (`content.js` の `handleLocalMask()`) も同じ上限で待つようになる。<br>8 秒の根拠: 判定そのものは 20,000 字でも 1.5 秒以内 (計測)。遅い端末で 3 倍かかっても収まる。キャッシュが温まる前の読み込み (13〜22 秒) は待ち切れないが、温まったあと (1 秒前後) は上限の中で終わる。加えて D-SC-12 の先読みで、ページを開いてから送るまでの間に読み込みが終わっていることが多い。読み込み中に送ると、8 秒待ってから正規表現と辞書だけで送る | F-SC-21 |
| D-SC-10 | 保護入力欄は、送れたあとに `ml.status` が `timeout` か `error` なら、動作ログに `ml.skipped` (`reason: timeout` / `error`、`where: send`) を残し、「ML の判定が間に合わなかったので、辞書と正規表現だけで伏せて送ったよ。」(失敗なら「ML の判定に失敗したので、…」) を 6 秒出す。<br>・「マスキングする」(D-SC-05) も同じ (`where: mask-draft`、「…だけで伏せたよ。」)<br>・マスキングがオフのときの送信では、ML は警告の件数にしか使わないので、記録も表示もしない<br>・確認で取り消したときと、送れなかったとき (`send.failed`) は記録しない。次に送るときに検出し直す | F-SC-21 |
| D-SC-11 | 検出が 0.3 秒で終わらなければ「確認中…」を出し、終わったら消す。ML なしの検出は数ミリ秒で終わるので、普段は出ない | F-SC-22 |
| D-SC-12 | `content.js` は、ページを開いて設定を読んだとき ML がオンなら `ML_PREWARM` を Service Worker に送る (ページごとに 1 回。開いている間にオンになったときも)。Service Worker は offscreen でモデルを読み込む。読み込み済みなら何もしない。保護入力欄 (iframe) からは送らない: content script は対応サイトすべてで動くので、ほかのサイトの経路にも効く。<br>残る穴: ブラウザを起動した直後は、offscreen の文書ができてから、その中のスクリプトが受け口を作るまでの間に送ったメッセージが「受け手が無い」で落ちることがある (1.3.0 から。計測中に冷えた起動 6 回のうち 1 回で起き、温まった状態の 12 回では起きなかった)。落ちると先読みは始まらず、最初の送信が 8 秒待って正規表現と辞書だけになる (一言と `ml.skipped` が出る)。設定画面の「ML 検出を有効化」をオンにした直後の読み込みでも同じ失敗が出うる。再現する手段が無いので 1.7.1 では直さず、次の版の課題にする | F-SC-23 |
