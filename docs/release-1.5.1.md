# 1.5.1 の修正

1.5.0 の送信経路の検証 (`tests/integration/verify-llm-masking.mjs`) で見つかった漏れを直す。検証の結果は `docs/llm-prompt-optimization.md` の「実際の送信経路での検証」にある。

## 問題

| ID | 問題 | 根拠 |
|---|---|---|
| P-01 | 伏せる範囲が重なると、伏せ字が壊れて元の文字の断片が送信される | 1.7B で「マイナンバーは <MY_NUMBER_1>89012」、4B で「<COMPANY_2>PANY_3>」 |
| P-02 | LLM が返した値を、英数字の語の途中でも見つけてしまう | 口座番号の「1234567」をマイナンバー「123456789012」の中でも見つけた |
| P-03 | 日本語の「パスワードは ○○」「パスワードを ○○ に変更」の値を拾えない | LLM なしで管理者パスワードがそのまま送信された |
| P-04 | ひらがなを含む社名を拾えない。記号 1 文字だけを社名として拾う | 「有限会社さくら物産」が「・有限会社」になった |
| P-05 | LLM が名字だけを返すと下の名前が残る。フルネームを返しても、文中で別に出てくる名字は伏せられない | 4B で「<PERSON_1> 智子」、「Anderson さん」がそのまま送信された |

P-01 の原因は 2 つある。

- 置き換えの処理が 4 か所にあり、どれも範囲の重なりを想定していない。3 か所は元の文字位置のまま右から置き換えるので、先に入れた伏せ字が途中で切れる。`aggregate.js` の 1 か所は重なった範囲の片方を捨てるので、はみ出した部分が伏せられない
- `injected.js` の `mergeLlmDetect()` は、正規表現の行と位置が重なる LLM の行も残す

| 場所 | 用途 |
|---|---|
| `injected.js` の `applyTriples()` | サイドバーで承認した内容を送信本文にする |
| `injected.js` の `applyTagSubstitutions()` | モーダル表示で承認した内容を送信本文にする |
| `sidebar.js` の `applyMasks()` | サイドバーの送信プレビュー |
| `engine/aggregate.js` の `applyTagMask()` | 正規表現だけの経路 |

## 要件

| ID | 要件 |
|---|---|
| R-01 | どれかの規則が伏せると決めた文字は、範囲が重なっていても、送信本文で必ず伏せられる |
| R-02 | 伏せ字は常に `<LABEL_N>` の形で、崩れない |
| R-03 | LLM の値は、英数字の語の途中では一致させない。日本語には語の区切りが無いので従来どおり |
| R-04 | 「パスワード」「暗証番号」「パスコード」の後に続く値を SECRET として拾う。「パスワードは8文字以上」「パスワードを変更」のような文は拾わない |
| R-05 | 「有限会社さくら物産」のように、ひらがなで始まる社名を拾う。記号だけの社名は拾わない |
| R-06 | 既存のテストベクター 232 件と、すべてのテストを壊さない |
| R-07 | LLM が人名の一部だけを返しても、同じ文章の中の名前の残りを伏せる |

## 設計

| ID | 決定 | 対応 |
|---|---|---|
| D-01 | `engine/aggregate.js` に `applySpans(text, spans)` を置く。重なる範囲は 1 つにまとめ、ラベルはその中で最も長い範囲のものにする。接しているだけの範囲はまとめない。番号は従来どおり、ラベルと文字列の組ごとに左から振る | R-01, R-02 |
| D-02 | 置き換えの 4 か所すべてを `applySpans()` に寄せる | R-01, R-02 |
| D-03 | `engine/aggregate.js` に `findOccurrences(text, value)` を置く。値の端が英数字なら、隣の文字も英数字である出現は除く。`mergeLlmDetect()` が使う | R-03 |
| D-04 | SECRET に、日本語の言い回しの後に続く値だけを拾うパターンを足す。値は ASCII の印字可能文字 4〜64 字に限る | R-04 |
| D-05 | COMPANY の 2 つのパターンを直す。法人格の後の社名はひらがなで始まってもよい。ただし助詞で終わるひらがなは除く。法人格の前の社名は、英数字・漢字・カタカナで始まる | R-05 |
| D-06 | `engine/aggregate.js` に `personSpans(text, value)` を置く。名字の直後に空白を挟んで短い語 (漢字 1〜3 字、カタカナ 2〜6 字) が続き、役職や敬称でなければ下の名前として含める。フルネームの各部分が単独で出る箇所も含める。`mergeLlmDetect()` が人名のラベルの値に使う | R-07 |

D-01 で範囲を捨てずにまとめるのは、どの規則の判断も「伏せる」方向にだけ働かせるためである。まとめた結果として本来より少し広く伏せることはあっても、漏れることはない。

## 検証

| ID | 確かめること | 場所 |
|---|---|---|
| T-01 | 重ならない範囲は従来どおり置き換わり、同じ文字列には同じ番号が付く | `tests/engine/apply-spans.test.mjs` |
| T-02 | 一方が他方を含む範囲、互いにはみ出す範囲が、どちらも 1 つの伏せ字になり、断片が残らない | 同上 |
| T-03 | 接しているだけの範囲は 2 つの伏せ字のままになる | 同上 |
| T-04 | 不正な範囲 (負、空、文字列の外) は無視する | 同上 |
| T-05 | 乱数で作った範囲でも、伏せ字が崩れず、伏せるべき文字が 1 つも残らない | 同上 |
| T-06 | `findOccurrences()` は英数字の語の途中を除き、日本語では従来どおり見つける | 同上 |
| T-07 | 日本語のパスワード表現と、誤検出させない例 | `tests/vectors/secret.json` |
| T-08 | ひらがなで始まる社名と、記号だけの社名を拾わないこと | `tests/vectors/company.json` |
| T-09 | 架空の個人情報を詰め込んだ文章で、壊れた伏せ字が 0、形式の値の漏れが 0 | `tests/integration/verify-llm-masking.mjs` |
| T-10 | 名字の後の下の名前を含め、役職や敬称は含めず、フルネームの部分も単独で見つける | `tests/engine/apply-spans.test.mjs` |

## 結果

架空の個人情報を詰め込んだ文章 (`tests/llm-eval/pii-rich.json`) を実際の送信経路に流して照合した。形式の値は 21 個、文脈の語は 20 個。

| モード | 版 | 形式の値を完全に伏せた | 文脈の語を完全に伏せた | 伏せてはいけない語を残した | 崩れた伏せ字 |
|---|---|---|---|---|---|
| LLM なし | 1.5.0 | 20 | 4 | 7/7 | 0 |
| LLM なし | 1.5.1 | 21 | 5 | 7/7 | 0 |
| qwen3:4b | 1.5.0 | 21 | 12 | 7/7 | 5 |
| qwen3:4b | 1.5.1 | 21 | 17 | 7/7 | 0 |
| qwen3:1.7b | 1.5.0 | 20 | 7 | 7/7 | 7 |
| qwen3:1.7b | 1.5.1 | 21 | 10 | 7/7 | 0 |

1.5.1 で残る見逃しは、LLM が拾わなかった語 (「経営企画室」「大阪支社」「Kestrel」など) で、置き換えの不具合によるものは無い。

そのほかの確認:

- 単体テスト 101 件、テストベクター 245 件がすべて成功
- 送信経路の E2E (`e2e-send-path.mjs`) が、開発版と提出用 zip の両方で成功
- LLM 経路の E2E (`e2e-llm-detect.mjs`) が 4B と 1.7B で成功
- 正規表現だけで、評価セット 56 件の「伏せてはいけない語」を新たに拾った例は 0 件
